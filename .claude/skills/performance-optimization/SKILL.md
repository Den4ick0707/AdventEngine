# Оптимізація продуктивності

## Головне правило
Спершу вимір, потім зміна. Код, який не виміряно, не оптимізується.
Вимірюй у пресеті `release` або `relwithdebinfo`: Debug і validation layers спотворюють картину.

## Порядок
1. Ціль у мілісекундах: 60 FPS = 16,67 мс, 120 FPS = 8,33 мс.
2. Відтворюваний найгірший сценарій.
3. Профіль: де вузьке місце — CPU (логіка, підготовка команд) чи GPU (шейдери, заповнення, пропускна здатність).
4. Виправлення однієї найбільшої витрати. Алгоритмічний виграш (менше роботи, кешування, рідше оновлення)
   важливіший за мікрооптимізацію.
5. Повторний вимір на тому самому сценарії. Залишити чи відкотити — за цифрами.
6. Звіт: було, стало, що знайдено, що змінено.

## Інструменти
| Що | Чим |
|----|-----|
| CPU, гарячі функції | `perf record -g`, `perf report`; `valgrind --tool=callgrind` |
| Кадр GPU, проходи, ресурси | RenderDoc |
| Час GPU в коді | `vkCmdWriteTimestamp2` з query pool |
| Пам'ять, витоки | `./dev p sandbox-asan`, VMA statistics (`vmaBuildStatsString`) |

## Типові виправлення
- **CPU:** немає виділень пам'яті в кадрі (перевикористання буферів, пули, лінійні алокатори);
  дані суцільними масивами; рідше оновлюй те, що змінюється рідко.
- **Підготовка команд:** менше draw calls і змін стану — інстансинг, спільні матеріали й пайплайни,
  сортування за пайплайном; згодом — indirect draw.
- **GPU:** менше перемальовування прозорих шарів, дешевші шейдери, менша роздільна здатність ефектів,
  LOD і відсікання невидимого.
- **Синхронізація:** очікування fence на кожному кадрі замість кадрів у польоті вбиває паралелізм CPU і GPU.

## Бюджети
Після виправлення зафіксуй бюджет (мс на підсистему, розміри текстур, кількість трикутників і draw calls),
щоб продуктивність не погіршувалася непомітно.
