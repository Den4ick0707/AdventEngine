# 0006. Modular architecture

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Проєкт розвиватиметься довго: після базового рендерингу й анімації — редактор, публічний реліз, апаратне
трасування променів. Головна відмінність від подібних рушіїв — модульність: легке ядро, до якого підключаються
модулі, зокрема написані іншими людьми. Потрібно визначити шари, місце редактора, спосіб підключення модулів
і ціну абстракції.

## Розглянуті варіанти

**Редактор**
1. **Окремий застосунок поверх рушія.** Код лише для редактора живе в модулі `editor`, гра його не підключає.
   Плюси: чіткі межі, гра не містить коду редактора. Мінуси: більше роботи на старті.
2. **Редактор вбудований у рушій**, будь-яку гру можна запустити в режимі редагування.
   Плюси: простіше почати. Мінуси: код редактора потрапляє в кожну гру.

**Підключення модулів**
1. **Статично**: модуль — бібліотека, яку обирають при збиранні.
   Плюси: нуль накладних витрат, повна оптимізація компілятором, немає проблем бінарної сумісності.
   Мінуси: новий модуль потребує перезбирання застосунку.
2. **Динамічно**: модуль — `.so`/`.dll`, завантажується під час роботи.
   Плюси: модулі поширюються окремо від рушія. Мінуси: стабільний ABI у C++ складний, різниця між ОС,
   втрата оптимізації між модулями.

## Рішення

**Шари** (залежності лише вниз):

```
apps       editor, sandbox, ігри
modules    renderer, scene, assets, animation, ...
kernel     реєстр модулів, головний цикл, події, сервіси
platform   вікно, ввід, файли, потоки
core       лог, assert, час, пам'ять, математика
```

- Редактор — окремий застосунок (варіант 1).
- Рендерер — модуль, як і решта; kernel нічого не знає про Vulkan.
- Модулі статичні (варіант 1), але описуються так, ніби можуть стати плагінами:
  маніфест з ім'ям, версією, автором, залежностями і мінімальною версією API рушія.
- Kernel будує порядок ініціалізації з маніфестів; цикл залежностей — помилка при збиранні.
- Сторонні модулі поширюються вихідним кодом: тека з маніфестом і CMake у `modules/`, збирається разом із рушієм.
- Межі між модулями грубі: виклик на модуль за кадр, обмін масивами даних. Віртуальних викликів на кожен
  об'єкт чи draw call немає.

## Наслідки
- `runtime` переростає в `kernel`; `Application` перестає володіти `VulkanContext`, рендерер стає модулем.
- Потрібна система модулів: маніфест, реєстр, порядок ініціалізації, сервіси й події. Її деталі, зокрема
  розв'язання циклічних залежностей, — окреме рішення.
- Потрібен інструмент для авторів модулів: створення заготовки, збирання з рушієм, пакування.
- Динамічні плагіни можна додати пізніше, не переписуючи модулі, якщо маніфест і реєстрація вже є.
