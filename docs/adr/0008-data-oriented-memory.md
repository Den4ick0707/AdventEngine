# 0008. Data-oriented design, memory and containers

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Рушій обробляє тисячі об'єктів щокадру: трансформації, суглоби, відсікання, фізика. Продуктивність таких систем
визначає розкладка даних у пам'яті, а не кількість інструкцій. У модульному рушії також треба бачити, скільки
пам'яті займає кожен модуль, і ловити витоки. Модулі мають посилатися на дані один одного без сирих вказівників.

## Розглянуті варіанти

**Розкладка даних**
1. **Масив структур (AoS) скрізь.** Звично, але система, що читає одне поле, тягне в кеш увесь об'єкт.
2. **Структура масивів (SoA) скрізь.** Максимум кешу для масової обробки, але незручно для поодиноких об'єктів.
3. **За способом доступу.** SoA для гарячих масових даних, звичайні структури для решти.

**Пам'ять**
1. **Стандартна купа.** Просто, але без обліку по модулях і без швидких тимчасових виділень.
2. **Власні контейнери з власними алокаторами.** Повний контроль, але багато коду.
3. **`std::pmr`.** Стандартні контейнери з підмінним джерелом пам'яті: облік і спеціалізовані алокатори без
   власних контейнерів. Ціна — віртуальний виклик на виділення.

**Сховище з посиланнями**
1. **Вказівники між модулями.** Висять після видалення, не серіалізуються.
2. **Slot map з handles.** Щільні масиви для ітерації, handle з поколінням для безпечного доступу.

## Рішення
- **Data-oriented design**: розкладка обирається за тим, як дані читають. Для гарячих даних, які системи
  обробляють масово, — SoA; для поодиноких об'єктів, описів і конфігурацій — звичайні структури.
- **Пам'ять через `std::pmr`**:
  - `TrackedResource` — облік на модуль: байти, кількість виділень, необов'язковий бюджет; усі ресурси
    реєструються в загальному реєстрі для статистики;
  - `FrameArena` — лінійний алокатор для даних одного кадру, скидається раз на кадр;
  - пули (`std::pmr::unsynchronized_pool_resource`) поверх обліку для дрібних однакових об'єктів;
  - `advent::make_unique<T>(resource, args...)` — власність з пам'яттю з ресурсу модуля;
  - глобальний `operator new` не підміняється.
- **Витоки**: у Debug реєстр перевіряє ресурси при знищенні; незвільнена пам'ять — `[error]` у лозі з назвою
  модуля і кількістю байтів, тож smoke-тест падає.
- **Дисципліна**: у `engine/` заборонено `std::vector`, `std::string`, `std::make_unique`, `new`; замість них —
  `std::pmr`-контейнери і `advent::make_unique`. Перевіряє `./dev` (скрипт, у CI теж); виняток у рядку —
  `// advent-allow: std-alloc`. Тести й застосунки правило не зачіпає.
- **`SoaPool<Tag, Columns...>`** — базове сховище: slot map із handles (індекс і покоління), щільні SoA-колонки,
  видалення через перенесення останнього елемента. Колонки — окремі `std::pmr::vector`; спосіб зберігання
  схований усередині й може змінитися без змін у користувачах.

## Наслідки
- Код рушія використовує `std::pmr::vector`, `std::pmr::string` і ресурс свого модуля.
- `VulkanContext`, `Window` і `log` переписуються під ці правила разом із появою `core`-примітивів.
- Порядок елементів у `SoaPool` змінюється при видаленні; дані, де порядок важливий (ієрархія), потребують
  окремої структури.
- Багатопотоковий доступ до арен і пулів — тема «Потоки»; лічильники обліку атомарні вже зараз.
