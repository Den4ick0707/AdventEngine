# 0010. Error handling: exceptions, Result and asserts

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Досі помилки оброблялися винятками (провал запуску), `ADVENT_ASSERT` (помилки програміста) і `ADVENT_VK_CHECK`.
З редактором з'являються помилки в нормальній роботі: пошкоджений файл моделі, відсутня сцена, помилка
в маніфесті модуля. Вони не повинні завершувати програму, а мають бути видимими й обробленими.

## Розглянуті варіанти
1. **Винятки скрізь.** Мало коду, але з сигнатури не видно, що функція може провалитися; легко не обробити.
2. **Тип-результат `Result<T>`.** Помилка видно в сигнатурі; `[[nodiscard]]` не дає її проігнорувати;
   ціна — одна перевірка. Потребує явних перевірок у коді.
3. **Коди помилок і вихідні параметри.** Легко проігнорувати; незручно передавати опис.

## Рішення

| Ситуація | Механізм |
|----------|----------|
| Провал запуску: немає GPU, драйвера, обов'язкового файлу | виняток (`std::runtime_error`, `renderer::VulkanError`) |
| Помилка в нормальній роботі: файли, імпорт, парсинг, модулі | `Result<T>` |
| Помилка програміста: порушений інваріант | `ADVENT_ASSERT` |

- `Result<T>` — власний тип у `core` з інтерфейсом `std::expected` (C++23): `operator bool`, `has_value`,
  `operator*`, `value`, `error`, `value_or`; `Result<void>` для функцій без значення. Позначений `[[nodiscard]]`.
- Зберігається на стеку (значення або помилка в одному місці), купу не використовує. Пул чи спільний екземпляр
  не потрібні.
- `Error`: `ErrorCode` (спільний для рушія: `not_found`, `invalid_data`, `io_error`, `unsupported`,
  `out_of_memory`, `version_mismatch`, ...) і текст для людини. Пам'ять для тексту — ресурс `core.errors`;
  виділяється лише при помилці.
- Помилка передається вгору явно (`if (!r) return r.error();`): оператора `?` у C++ немає, а макроси на
  розширеннях GCC і Clang не працюють у MSVC.

## Наслідки
- Функції, що можуть не вдатися в нормальній роботі, повертають `Result<T>`.
- При переході на C++23 `Result` можна замінити на `std::expected` майже без змін у коді.
