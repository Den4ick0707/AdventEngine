# 0014. Single-threaded frame now, job system later

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Рушій однопотоковий, а процесори мають 8–16 ядер. Багатопотоковість потрібна для продуктивності, але
помилки синхронізації важко відтворити, а розподіл роботи неможливо обґрунтувати без реальних навантажень.

## Розглянуті варіанти
1. **Окремі потоки на підсистеми** (рендер, завантаження, головний). Зрозуміло, але використовує 2–3 ядра
   і погано масштабується.
2. **Система задач зараз.** Використовує всі ядра і пасує до SoA, але проєктується наосліп, без навантажень.
3. **Однопотоковий кадр зараз, система задач пізніше**, з правилами, які роблять перехід безболісним.

## Рішення
Варіант 3.
- Кадр виконується в одному потоці. GPU працює паралельно (два кадри в польоті).
- Цільова модель — система задач: пул потоків, задачі із залежностями, `parallel_for` над SoA-колонками.
- Вже зараз діють правила потокобезпечного дизайну: без прихованого глобального стану, явні вхідні й вихідні
  дані систем, розділення читання і запису, атомарні лічильники обліку, callback-и лише записують дані.
- Перехід поетапний, кожен крок — після вимірювань і з окремим ADR.

Деталі, правила і порядок переходу — [docs/threading.md](../threading.md).

## Наслідки
- Модулі пишуться так, ніби їх системи колись виконуватимуться паралельно.
- Першим кроком стане фонове завантаження ассетів.
