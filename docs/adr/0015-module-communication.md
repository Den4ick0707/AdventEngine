# 0015. Module communication: dependencies, services, events, shared data

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Модулі (ADR 0006) мають знаходити один одного і обмінюватися інформацією, не порушуючи модульності
і не втрачаючи продуктивності. Зв'язки бувають різні: обов'язкова залежність, замінна реалізація,
рідкісне сповіщення, масовий обмін даними щокадру. Для шутерів і подібних ігор не можна додавати
затримку між вводом і результатом на екрані.

## Розглянуті варіанти
- **Один механізм на все** (лише події або лише прямі виклики). Або повільно для масових даних, або
  жорстке зв'язування модулів.
- **Події як callback-и.** Виклик чужого коду в довільний момент, виклик на кожну подію, складно з потоками.
- **Події як масиви з подвійним буфером.** Просто, але додає кадр затримки навіть у природному порядку.
- **Події як масиви з закладкою на читача.** Без затримки в природному порядку, без втрат подій.

## Рішення
Чотири механізми, кожен для своєї ситуації. Усе модуль отримує через `ModuleContext` від kernel,
глобальних синглтонів немає.

| Ситуація | Механізм | Ціна |
|----------|----------|------|
| Обов'язкова залежність (`scene` потребує `assets`) | `ctx.require<assets::AssetsModule>()`: пряме посилання; залежність має бути в маніфесті, kernel ініціалізує її раніше | звичайний виклик |
| Замінна реалізація (Vulkan-рендерер або заглушка) | сервіс через інтерфейс: `ctx.service<IRenderer>()` | віртуальний виклик на грубій межі |
| Сповіщення (вікно змінило розмір, ассет перезавантажено) | події як масиви | дописування в масив, прохід по масиву |
| Масовий обмін даними щокадру (матриці суглобів, трансформації) | спільні SoA-дані: один модуль пише колонки, інший читає | без накладних витрат |

**Події:**
- Кожен тип події — масив (`publish` дописує елемент, пам'ять з `FrameArena`).
- Подія видима одразу після публікації. Кожен читач має власну закладку і бачить кожну подію рівно один раз.
- Читач, що йде в кадрі після того, хто публікує, бачить подію в тому самому кадрі; читач, що йде раніше, —
  на початку наступного.
- Події зберігаються два кадри, потім видаляються; пропустити подію неможливо.

**Затримка вводу:** ланцюжок ввід → симуляція → рендер іде через дані (стан вводу читається напряму),
події в ньому не використовуються.

## Наслідки
- Kernel надає `ModuleContext` з `require`, `service`, `events`.
- `require` дозволений лише для модулів із маніфесту; порушення — помилка при ініціалізації.
- Розташування спільних даних (сцена, ECS) — тема «Сцена».
