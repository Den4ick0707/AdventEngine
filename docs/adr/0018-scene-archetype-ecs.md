# 0018. Scene: archetype ECS with tables, command buffers and sparse components

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Сцена — спільні дані, через які модулі обмінюються інформацією щокадру (ADR 0015): трансформації,
меші, скелети, камери. Розкладка має бути SoA (ADR 0008), посилання між модулями — handles (ADR 0009),
обробка — системами у фазах кадру (ADR 0016). Редактору потрібні окрема сцена для редагування і копія для запуску.

## Розглянуті варіанти
- **Граф сцени** (дерево об'єктів з компонентами). Інтуїтивно, але дані розкидані по пам'яті, суперечить SoA.
- **EnTT.** Перевірена бібліотека, але нова залежність із власною пам'яттю й handles, що дублюють
  `SoaPool` і `TrackedResource`.
- **Власна ECS, sparse set** (пул на тип компонента). Проста, дешеве додавання компонентів, але прохід
  по кількох компонентах разом повільніший.
- **Власна ECS, archetype** (сутності з однаковим набором компонентів зберігаються разом). Найшвидший
  прохід по кількох компонентах, складніша реалізація, зміна набору компонентів переносить сутність.

## Рішення
Власна ECS на archetype-ах у модулі `scene`.

**Зберігання:**
- Сутність — `Handle<Entity>`. Запис сутності в `SoaPool` зберігає її місце: archetype і рядок.
- Archetype — таблиця для одного набору компонентів; кожен компонент — окрема колонка (`std::pmr`, ресурс модуля).
- Зараз — **таблиці**: колонка є одним масивом, що росте. Пізніше — **чанки** фіксованого розміру
  (зручніше ділити між потоками, без великих перевиділень). Інтерфейс запитів від цього не залежить;
  перехід — окремим ADR.
- Archetype запам'ятовує переходи «додати або прибрати компонент X → archetype Y», щоб не шукати їх щоразу.
- Компонент, що часто вмикається і вимикається (маркери «вибрано», «горить»), реєструється як **sparse**:
  зберігається в окремому пулі, не входить у archetype, і його зміна не переносить сутність.

**Доступ:**
- Запит `world.query<LocalTransform, WorldTransform>()` знаходить відповідні archetype-и, кешує список
  і проходить колонками лінійно. Новий archetype додається до кешів запитів при створенні.
- Модулі реєструють свої типи компонентів при ініціалізації (`animation` — `Skeleton`, `renderer` — `MeshRenderer`).

**Структурні зміни** (створення і видалення сутностей, додавання і прибирання компонентів, зміна ієрархії)
виконуються лише через `CommandBuffer`. Системи записують команди, kernel застосовує буфер між системами.
Поки система проходить таблицю, її структура не змінюється; це ж правило потрібне для системи задач (ADR 0014).
Зміна значень компонентів — напряму.

**Світи:** `World` — окремий набір сутностей і компонентів. Їх може бути кілька: редактор тримає сцену
для редагування і копію для запуску (Play).

**Трансформації й ієрархія:**
- `LocalTransform` — позиція (`vec3`), обертання (`quat`), масштаб (`vec3`, різний по осях). Пишуть геймплей,
  фізика, анімація, редактор.
- `WorldTransform` — `mat4`, обчислюється системою, вручну не пишеться. Читають рендерер, камера, трасування.
- `Hierarchy { parent, first_child, next_sibling, prev_sibling }` — зв'язний список із фіксованим розміром,
  без виділень пам'яті, прикріплення і відкріплення за O(1). Сутність без `Hierarchy` — корінь;
  пласкі сцени за ієрархію не платять.
- Система `scene.propagate_transforms` виконується один раз за кадр, на початку `late_update`: після фізики,
  геймплею й анімації. Перераховуються лише гілки зі зміненим `LocalTransform`.
- Постійний ідентифікатор сутності — компонент `Uuid` (для файлів і посилань між сценами); handle діє лише під час роботи.

## Наслідки
- Система в `late_update`, що змінює `LocalTransform` (наприклад, камера), сама оновлює свій `WorldTransform`
  через функцію модуля `scene`, інакше рендер побачить зміну лише в наступному кадрі.
- Kernel отримує точки застосування `CommandBuffer` між системами.
- Інтерполяція між кроками фізики (`alpha`) вирішується в темі «Фізика», ймовірно через `PreviousTransform`.
- Подвійна точність для великих світів — пізніше, за потреби.
- Формат збереження світу — тема «Серіалізація».
