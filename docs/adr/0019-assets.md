# 0019. Assets: meta files, runtime import, explicit reference counts

- Статус: Accepted
- Дата: 2026-11-05

## Контекст
Сцени посилаються на меші, текстури, матеріали, скелети й анімації. Посилання у файлах мають переживати
перейменування і переміщення (ADR 0009), а під час роботи доступ має бути через handles, сумісні з компонентами
ECS (ADR 0018). Редактору потрібне гаряче перезавантаження, а системі задач (ADR 0014) — фонове завантаження.

## Розглянуті варіанти
**Формат, який завантажує гра:**
- **Джерела напряму** (`.gltf`, `.png`) через імпортер під час роботи. Просто, але повільніше завантаження
  і сирі файли в грі.
- **Власний бінарний формат** у кеші `project://.cache/`. Швидке завантаження, стиснення текстур під GPU,
  але потрібні формат, парсер і кешування — зараз зайве.

**Постійний ідентифікатор:**
- **Файл-супутник `.meta`** поруч із джерелом. Надійно з git, зрозуміло людині.
- **Одна база `uuid → шлях`.** Губить зв'язки при переміщенні поза редактором, конфліктує при злитті.

**Час життя:**
- **Автоматичний лічильник у handle.** Зручно, але компоненти ECS перестають бути простими даними.
- **Явний лічильник** (`acquire` і `release`). Handles лишаються простими даними.

## Рішення
- Гра імпортує джерела під час роботи; власного формату поки немає.
- Імпорт — окремий крок: `джерело -> Importer -> CPU-дані (MeshData, TextureData, ...) -> реєстр`.
  Власний формат пізніше додається кешем між імпортером і реєстром, окремим ADR; решта рушія не змінюється.
- Кожне джерело має `<file>.meta` (JSON, комітиться разом із джерелом): `Uuid` і налаштування імпорту.
  Файл із кількома ассетами (glTF) розкладається на під-ассети, кожен зі своїм `Uuid` у тому ж `.meta`:

  ```json
  {
    "uuid": "6f1c2e9a-...",
    "importer": "gltf",
    "settings": { "scale": 1.0 },
    "sub_assets": {
      "mesh/Body": "a41d...",
      "material/Skin": "93be...",
      "animation/run": "0c7f..."
    }
  }
  ```

  `.meta` створюється при першому імпорті; відсутній або пошкоджений `.meta` — `[warn]` і новий `Uuid`.
- Під час роботи — `AssetHandle<T>` (звичайний `Handle`, прості дані). Реєстр перетворює `Uuid` на handle.
- Явний лічильник: хто завантажує, той звільняє (`acquire` і `release`; сцена — для всіх ассетів, на які
  посилається). Ассет із нулем посилань вивантажується в `end_frame`, не раніше ніж через два кадри
  (кадри в польоті на GPU).
- Інтерфейс асинхронний: `load` одразу повертає handle, стан — `loading`, `ready` або `failed`.
  Перша реалізація синхронна; фонове завантаження — перший крок переходу на потоки (ADR 0014).
- Поки ассет не готовий або не завантажився, використовується запасний (рожева текстура, куб);
  помилка — у лозі, гра не падає.
- Гаряче перезавантаження в редакторі й dev-збірці: platform стежить за `project://assets/`, змінене джерело
  імпортується знову, нові дані стають під той самий handle, публікується подія `AssetReloaded`
  (ADR 0015); рендерер оновлює GPU-копію. У грі вимкнено.
- Модуль `assets` повертає лише CPU-дані; GPU-ресурси за handle ассета створює рендерер.

## Наслідки
- cgltf і stb потрапляють у збірку гри; mip-рівні генеруються під час завантаження.
- Імпортери живуть у модулі `assets`, а не в `editor`, поки гра імпортує сама. З появою власного формату
  вони переходять у модуль `kind: editor`.
- `platform` отримує спостереження за змінами файлів (лише dev і редактор).
- Незбалансовані `acquire` і `release` у Debug — `[error]` при завершенні з переліком ассетів.
