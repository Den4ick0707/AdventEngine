# Архітектура

AdventEngine — модульний 3D-рушій на C++20 і Vulkan 1.3. Основа — легке ядро, до якого підключаються модулі:
рендерер, сцена, ассети, анімація, у майбутньому трасування променів, фізика, аудіо. Редактор, демо і ігри —
окремі застосунки поверх рушія.

Документ описує прийняті рішення і поточний стан. Обґрунтування кожного рішення — в [ADR](adr/README.md).
Теми, які ще обговорюються, зібрано в розділі «Відкриті питання».

## Принципи

- **Модульність.** Ядро мінімальне; функціональність додається модулями, які можна вмикати й вимикати при збиранні.
- **Data-oriented design.** Розкладка даних обирається за тим, як їх читають: SoA для гарячих даних, які системи
  обробляють масово; звичайні структури для поодиноких об'єктів і конфігурацій.
- **Межі без втрати продуктивності.** Модулі взаємодіють великими порціями даних: виклик на модуль за кадр,
  масиви команд. Віртуальних викликів на кожен об'єкт, сутність чи draw call немає.
- **CPU-дані окремо від GPU.** Ассети й анімація повертають CPU-структури; лише рендерер знає про Vulkan.
- **Явне володіння.** RAII для всіх ресурсів, без прихованого глобального стану.
- **Довгостроковість.** Рішення приймаються з розрахунку на розвиток проєкту, а не на одну демонстрацію.

## Шари

[ADR 0006](adr/0006-modular-architecture.md)

```
apps          editor, sandbox, ігри
   |
modules       renderer, scene, assets, animation, input, (raytracing, physics, audio, ...)
   |
kernel        реєстр модулів, головний цикл, події, сервіси
   |
platform      вікно, ввід, файли, потоки
   |
core          лог, assert, час, пам'ять, математика; без залежностей від ОС
```

Залежності спрямовані лише вниз. Модуль може залежати від `kernel`, `platform`, `core` та інших модулів,
оголошених у його маніфесті. Цикли між модулями заборонені й виявляються при збиранні.

## Правила залежностей

- `core` залежить лише від GLM.
- `platform` залежить від `core`; GLFW видно лише в `platform/src` (і приватно в `renderer/src` для surface).
- Vulkan-типи живуть лише в модулі `renderer`. Інші модулі передають йому CPU-дані.
- `assets` і `animation` нічого не знають про GPU.
- Код, потрібний лише редактору (інспектори, гізмо, імпорт), живе в модулі `editor`, який гра не підключає.
- Зміна правил залежностей або структури модулів — лише через ADR.

## Поточний стан

| Компонент | Шар | Стан | Зміст |
|-----------|-----|------|-------|
| `core` | core | частково | є `log`, `ADVENT_ASSERT`, `FrameClock`, `FixedTimestep`; далі пам'ять, `SoaPool`, ідентифікатори, `Result` |
| `platform` | platform | готово | `Window`: події, розмір framebuffer, Vulkan-розширення |
| `runtime` | kernel | частково | `Application` (головний цикл), `Module`, `run_application` |
| `renderer` | модуль | в роботі | `VulkanContext`, `ADVENT_VK_CHECK`; далі swapchain |
| `assets` | модуль | заплановано | glTF і текстури в CPU-дані (cgltf, stb) |
| `animation` | модуль | заплановано | скелет, кліпи, семплінг, матриці суглобів |
| `scene` | модуль | заплановано | archetype ECS, трансформації, ієрархія |
| `input` | модуль | заплановано | дії й прив'язки поверх сирого вводу platform |
| `apps/sandbox` | застосунок | готово | демо для ручної перевірки і smoke-тесту |
| `apps/editor` | застосунок | заплановано | редактор сцени |

Відхилення від цільової архітектури, які треба усунути:
- `runtime` — зародок `kernel`, але `Application` напряму володіє `Window` і `VulkanContext`.
  У цільовій архітектурі рендерер підключається як модуль, а `Application` нічого не знає про Vulkan.
- `runtime::Module` — заготовка: немає маніфесту, залежностей між модулями і порядку ініціалізації.

## Модулі

ADR [0006](adr/0006-modular-architecture.md), [0017](adr/0017-module-manifest.md).

- Модуль — статична бібліотека, яку обирають при збиранні. Накладних витрат на виклики немає.
- Модуль описується маніфестом `module.json`: ім'я, версія, опис, автор, ліцензія, сумісні версії API рушія,
  вид (`runtime` — у грі, `editor` — лише в редакторі), обов'язкові й необов'язкові залежності, сервіси.
- Цикли залежностей — помилка конфігурації CMake з переліком модулів. Розриваються винесенням спільного
  в нижчий модуль, сервісом-інтерфейсом або подіями.
- Kernel будує порядок ініціалізації за залежностями: ініціалізація в топологічному порядку, завершення — у зворотному.
- Сторонні модулі поширюються вихідним кодом: тека з маніфестом і CMake кладеться в `modules/` і збирається
  разом із рушієм. Скомпільовані бібліотеки не поширюються: вони прив'язані до компілятора і його прапорців.
- Для авторів модулів планується інструмент: створити заготовку, зібрати з рушієм, запакувати для поширення.

### Зв'язки між модулями

[ADR 0015](adr/0015-module-communication.md). Усе модуль отримує через `ModuleContext` від kernel.

| Ситуація | Механізм |
|----------|----------|
| Обов'язкова залежність | `ctx.require<Module>()`: пряме посилання, лише на модулі з маніфесту |
| Замінна реалізація | сервіс через інтерфейс: `ctx.service<IRenderer>()` |
| Сповіщення | події як масиви: видимі одразу, закладка на читача, зберігаються два кадри |
| Масовий обмін щокадру | спільні SoA-дані |

Ланцюжок ввід → симуляція → рендер іде через дані, без подій, тож не має зайвої затримки.
Спільні дані щокадру — компоненти сцени (розділ «Сцена»).

## Core

Фундамент для всіх шарів. Рішення — ADR [0008](adr/0008-data-oriented-memory.md),
[0009](adr/0009-identifiers.md), [0010](adr/0010-error-handling.md), [0011](adr/0011-logging.md).

| Частина | Що є |
|---------|------|
| Пам'ять | `std::pmr`: `TrackedResource` (облік і бюджет на модуль, реєстр для статистики), `FrameArena` (дані одного кадру), пули, `advent::make_unique`; витік у Debug — `[error]` |
| Контейнери | `std::pmr`-контейнери; `SoaPool<Tag, Columns...>` — slot map з handles і щільними SoA-колонками |
| Ідентифікатори | `Handle<Tag>` (індекс і покоління, лише під час роботи), `Uuid` 128 біт (у файлах), `StringId` (хеш імені) |
| Помилки | винятки — провал запуску; `Result<T>` — помилки в нормальній роботі; `ADVENT_ASSERT` — помилки програміста |
| Лог | категорії модулів з рівнями, sink-и (консоль, файл завжди, редактор), форматування без виділень |
| Час | `FrameClock`, `FixedTimestep` |

Стан: рішення прийнято, реалізація заплановано на етап 2 [плану](roadmap.md).

## Платформа

Ізолює рушій від ОС. Рішення — ADR [0012](adr/0012-virtual-file-system-and-projects.md),
[0013](adr/0013-input-layers.md).

| Частина | Рішення |
|---------|---------|
| Файли | віртуальні шляхи `engine://`, `project://`, `user://`; `fs::Path` у core, монтування й доступ до диска в platform; помилки — `Result` |
| Проєкт | `<Name>.advent` (JSON) у корені проєкту: назва, `Uuid`, версія рушія, стартова сцена, модулі, точки монтування; лише відносні шляхи |
| Налаштування | рушій → проєкт → `user://settings.json` → командний рядок |
| Логи | Debug — поруч із виконуваним файлом, Release — `user://logs/` |
| Ввід | сирий стан пристроїв на кадр у platform; дії й прив'язки — модуль `input` |
| Вікна | `Window` на GLFW; API не припускає єдиного вікна, кілька вікон — тема «Редактор» |

## Потоки

[ADR 0014](adr/0014-single-threaded-frame.md). Кадр поки однопотоковий; цільова модель — система задач
(пул потоків, `parallel_for` над SoA-колонками). Правила, що діють уже зараз, і порядок переходу —
[docs/threading.md](threading.md).

## Сцена

[ADR 0018](adr/0018-scene-archetype-ecs.md). Власна ECS на archetype-ах у модулі `scene`.

| Частина | Рішення |
|---------|---------|
| Сутність | `Handle<Entity>`; запис у `SoaPool` зберігає archetype і рядок |
| Зберігання | archetype — таблиця з колонкою на компонент; зараз масиви, що ростуть, пізніше чанки |
| Sparse-компоненти | компоненти, що часто вмикаються (маркери), — в окремих пулах, без перенесення сутності |
| Запити | `world.query<A, B>()`: кешований список archetype-ів, лінійний прохід колонками |
| Структурні зміни | лише через `CommandBuffer`; kernel застосовує його між системами |
| Світи | кілька `World`: редактор тримає сцену для редагування і копію для запуску |
| Трансформації | `LocalTransform` (позиція, `quat`, масштаб `vec3`) пишуть системи; `WorldTransform` (`mat4`) обчислює `scene.propagate_transforms` на початку `late_update`, лише для змінених гілок |
| Ієрархія | `Hierarchy`: parent, first_child, next_sibling, prev_sibling; без компонента — корінь |
| Постійний ID | компонент `Uuid` для файлів і посилань між сценами |

Модулі реєструють власні типи компонентів при ініціалізації. Інтерполяція між кроками фізики — тема «Фізика».

## Головний цикл

ADR [0004](adr/0004-main-loop-fixed-timestep.md), [0016](adr/0016-frame-phases-and-systems.md).

```
begin_frame -> fixed_update x N -> update -> late_update -> render(alpha) -> end_frame
```

- Kernel ділить кадр на фази; модулі й застосунок реєструють у них системи:
  `ctx.add_system(Phase::update, "animation.joints", fn).after("animation.sample")`.
- Порядок у фазі — залежності модулів плюс явні `after`/`before`; будується при запуску, цикл — помилка.
- Поточний код ще використовує `Application` з `on_fixed_update`, `on_update`, `on_render`;
  перехід на фази — етап «Ядро і система модулів».

- `fixed_update` — фіксований крок, 60 Гц за замовчуванням: фізика, геймплей.
- `update` і `late_update` — раз на кадр зі змінним кроком: анімація, логіка, камера.
- `render` отримує `alpha` в [0, 1) для інтерполяції між станами симуляції.
- `FrameClock` обмежує крок до 0,25 с; `FixedTimestep` виконує не більше 8 кроків за кадр.
- Поки вікно згорнуте, цикл чекає подій і не навантажує процесор.

## Рендерер

- Vulkan 1.3, обов'язкові можливості: `dynamicRendering`, `synchronization2`. Render pass і framebuffer-об'єкти
  не використовуються.
- Функції Vulkan завантажує volk, пам'ять GPU виділяє VMA. Заголовки Vulkan — з `vendor/`, а не з SDK.
- Два кадри в польоті (`k_frames_in_flight = 2`); ресурси, що змінюються щокадру, дублюються на кожен кадр.
- Помилки Vulkan перевіряються `ADVENT_VK_CHECK`; повідомлення validation layers потрапляють у лог
  з позначкою джерела (`[vulkan:validation]`, `[vulkan:performance]`, `[vulkan:general]`).

### Трасування променів

Апаратне трасування променів — запланований окремий модуль. Щоб не переробляти рендерер пізніше:
- можливості `VK_KHR_acceleration_structure`, `VK_KHR_ray_tracing_pipeline`, `VK_KHR_ray_query` вмикаються
  як необов'язкові: рушій працює без них, а модуль трасування стає доступним, лише якщо GPU їх підтримує;
- вершинні й індексні буфери створюються з прапорцями, потрібними для побудови acceleration structures
  (`SHADER_DEVICE_ADDRESS`, `ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY`), коли трасування доступне;
- організація ресурсів і дескрипторів обирається так, щоб шейдери трасування мали доступ до всіх матеріалів сцени.

Конкретні рішення приймаються в темі «Рендерер» (див. нижче).

## Відкриті питання

Архітектура обговорюється по темах. Кожне рішення фіксується в ADR, після чого цей документ оновлюється.

| Тема | Що вирішити | Стан |
|------|-------------|------|
| 1. Загальна будова | шари, редактор, модулі | вирішено ([ADR 0006](adr/0006-modular-architecture.md)) |
| 2. Core | пам'ять, контейнери, ідентифікатори, помилки, лог | вирішено (ADR 0008–0011) |
| 3. Платформа | файли, проєкт, налаштування, ввід | вирішено (ADR 0012–0013) |
| 4. Потоки | однопотоковий кадр чи система задач, коли її вводити | вирішено ([ADR 0014](adr/0014-single-threaded-frame.md)) |
| 5. Рендерер | ресурси, дескриптори (класичні чи bindless), render graph, шейдери, трасування променів, напрям осі Y | відкрито |
| 6. Ассети | імпорт під час роботи чи власний формат, handles, гаряче перезавантаження | відкрито |
| 7. Сцена | граф сцени чи ECS (EnTT або власний) | вирішено ([ADR 0018](adr/0018-scene-archetype-ecs.md)) |
| 8. Анімація | семплінг, змішування, стан-машина | відкрито |
| 9. Серіалізація | формат сцен і проєктів | відкрито |
| 10. Редактор | бібліотека UI (Dear ImGui чи інша), функції першої версії, як модулі `kind: editor` розширюють редактор, кілька вікон | відкрито |
| 11. Розповсюдження | пакування, версіонування API, інструмент для модулів | відкрито |
| Система модулів | зв'язки, фази кадру, маніфест, цикли | вирішено (ADR 0015–0017) |
| Тестування | фреймворк (doctest чи Catch2) | відкрито |
| Фізика | власна чи бібліотека, інтерполяція між кроками (`PreviousTransform`) | відкрито |
