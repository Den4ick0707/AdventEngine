# Архітектура

AdventEngine — модульний 3D-рушій на C++20 і Vulkan 1.3. Основа — легке ядро, до якого підключаються модулі:
рендерер, сцена, ассети, анімація, у майбутньому трасування променів, фізика, аудіо. Редактор, демо і ігри —
окремі застосунки поверх рушія.

Документ описує прийняті рішення і поточний стан. Обґрунтування кожного рішення — в [ADR](adr/README.md).
Теми, які ще обговорюються, зібрано в розділі «Відкриті питання».

## Принципи

- **Модульність.** Ядро мінімальне; функціональність додається модулями, які можна вмикати й вимикати при збиранні.
- **Межі без втрати продуктивності.** Модулі взаємодіють великими порціями даних: виклик на модуль за кадр,
  масиви команд. Віртуальних викликів на кожен об'єкт, сутність чи draw call немає.
- **CPU-дані окремо від GPU.** Ассети й анімація повертають CPU-структури; лише рендерер знає про Vulkan.
- **Явне володіння.** RAII для всіх ресурсів, без прихованого глобального стану.
- **Довгостроковість.** Рішення приймаються з розрахунку на розвиток проєкту, а не на одну демонстрацію.

## Шари

[ADR 0006](adr/0006-modular-architecture.md)

```
apps          editor, sandbox, ігри
   |
modules       renderer, scene, assets, animation, (raytracing, physics, audio, ...)
   |
kernel        реєстр модулів, головний цикл, події, сервіси
   |
platform      вікно, ввід, файли, потоки
   |
core          лог, assert, час, пам'ять, математика; без залежностей від ОС
```

Залежності спрямовані лише вниз. Модуль може залежати від `kernel`, `platform`, `core` та інших модулів,
оголошених у його маніфесті. Цикли між модулями заборонені й виявляються при збиранні.

## Правила залежностей

- `core` залежить лише від GLM.
- `platform` залежить від `core`; GLFW видно лише в `platform/src` (і приватно в `renderer/src` для surface).
- Vulkan-типи живуть лише в модулі `renderer`. Інші модулі передають йому CPU-дані.
- `assets` і `animation` нічого не знають про GPU.
- Код, потрібний лише редактору (інспектори, гізмо, імпорт), живе в модулі `editor`, який гра не підключає.
- Зміна правил залежностей або структури модулів — лише через ADR.

## Поточний стан

| Компонент | Шар | Стан | Зміст |
|-----------|-----|------|-------|
| `core` | core | готово | `log`, `ADVENT_ASSERT`, `FrameClock`, `FixedTimestep` |
| `platform` | platform | готово | `Window`: події, розмір framebuffer, Vulkan-розширення |
| `runtime` | kernel | частково | `Application` (головний цикл), `Module`, `run_application` |
| `renderer` | модуль | в роботі | `VulkanContext`, `ADVENT_VK_CHECK`; далі swapchain |
| `assets` | модуль | заплановано | glTF і текстури в CPU-дані (cgltf, stb) |
| `animation` | модуль | заплановано | скелет, кліпи, семплінг, матриці суглобів |
| `scene` | модуль | заплановано | сутності, трансформації, ієрархія |
| `apps/sandbox` | застосунок | готово | демо для ручної перевірки і smoke-тесту |
| `apps/editor` | застосунок | заплановано | редактор сцени |

Відхилення від цільової архітектури, які треба усунути:
- `runtime` — зародок `kernel`, але `Application` напряму володіє `Window` і `VulkanContext`.
  У цільовій архітектурі рендерер підключається як модуль, а `Application` нічого не знає про Vulkan.
- `runtime::Module` — заготовка: немає маніфесту, залежностей між модулями і порядку ініціалізації.

## Модулі

[ADR 0006](adr/0006-modular-architecture.md). Деталі системи модулів (сервіси, події, розв'язання циклів) —
відкрите питання.

- Модуль — статична бібліотека, яку обирають при збиранні. Накладних витрат на виклики немає.
- Модуль описується маніфестом: ім'я, версія, автор, залежності від інших модулів, мінімальна версія API рушія.
- Kernel будує порядок ініціалізації за залежностями: ініціалізація в топологічному порядку, завершення — у зворотному.
- Сторонні модулі поширюються вихідним кодом: тека з маніфестом і CMake кладеться в `modules/` і збирається
  разом із рушієм. Скомпільовані бібліотеки не поширюються: вони прив'язані до компілятора і його прапорців.
- Для авторів модулів планується інструмент: створити заготовку, зібрати з рушієм, запакувати для поширення.

## Головний цикл

[ADR 0004](adr/0004-main-loop-fixed-timestep.md)

```
poll events -> on_fixed_update(step) x N -> on_update(dt) -> модулі -> on_render(alpha)
```

- `on_fixed_update` — фіксований крок, 60 Гц за замовчуванням: фізика, геймплей.
- `on_update` — раз на кадр зі змінним кроком: анімація, камера, UI.
- `on_render(alpha)` — `alpha` в [0, 1) для інтерполяції між станами симуляції.
- `FrameClock` обмежує крок до 0,25 с; `FixedTimestep` виконує не більше 8 кроків за кадр.
- Поки вікно згорнуте, цикл чекає подій і не навантажує процесор.

## Рендерер

- Vulkan 1.3, обов'язкові можливості: `dynamicRendering`, `synchronization2`. Render pass і framebuffer-об'єкти
  не використовуються.
- Функції Vulkan завантажує volk, пам'ять GPU виділяє VMA. Заголовки Vulkan — з `vendor/`, а не з SDK.
- Два кадри в польоті (`k_frames_in_flight = 2`); ресурси, що змінюються щокадру, дублюються на кожен кадр.
- Помилки Vulkan перевіряються `ADVENT_VK_CHECK`; повідомлення validation layers потрапляють у лог
  з позначкою джерела (`[vulkan:validation]`, `[vulkan:performance]`, `[vulkan:general]`).

### Трасування променів

Апаратне трасування променів — запланований окремий модуль. Щоб не переробляти рендерер пізніше:
- можливості `VK_KHR_acceleration_structure`, `VK_KHR_ray_tracing_pipeline`, `VK_KHR_ray_query` вмикаються
  як необов'язкові: рушій працює без них, а модуль трасування стає доступним, лише якщо GPU їх підтримує;
- вершинні й індексні буфери створюються з прапорцями, потрібними для побудови acceleration structures
  (`SHADER_DEVICE_ADDRESS`, `ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY`), коли трасування доступне;
- організація ресурсів і дескрипторів обирається так, щоб шейдери трасування мали доступ до всіх матеріалів сцени.

Конкретні рішення приймаються в темі «Рендерер» (див. нижче).

## Відкриті питання

Архітектура обговорюється по темах. Кожне рішення фіксується в ADR, після чого цей документ оновлюється.

| Тема | Що вирішити | Стан |
|------|-------------|------|
| 1. Загальна будова | шари, редактор, модулі | вирішено ([ADR 0006](adr/0006-modular-architecture.md)) |
| 2. Core | алокатори, помилки, контейнери, ідентифікатори і handles | відкрито |
| 3. Платформа | ввід, файлова система, час | відкрито |
| 4. Потоки | однопотоковий кадр чи система задач, коли її вводити | відкрито |
| 5. Рендерер | ресурси, дескриптори (класичні чи bindless), render graph, шейдери, трасування променів, напрям осі Y | відкрито |
| 6. Ассети | імпорт під час роботи чи власний формат, handles, гаряче перезавантаження | відкрито |
| 7. Сцена | граф сцени чи ECS (EnTT або власний) | відкрито |
| 8. Анімація | семплінг, змішування, стан-машина | відкрито |
| 9. Серіалізація | формат сцен і проєктів | відкрито |
| 10. Редактор | бібліотека UI (Dear ImGui чи інша), функції першої версії | відкрито |
| 11. Розповсюдження | пакування, версіонування API, інструмент для модулів | відкрито |
| Система модулів | сервіси, події, розв'язання циклів, маніфест | відкрито |
| Тестування | фреймворк (doctest чи Catch2) | відкрито |
