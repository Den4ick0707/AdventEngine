# Багатопотоковість

Рішення — [ADR 0014](adr/0014-single-threaded-frame.md). Документ описує поточний стан, правила, які діють
уже зараз, і план переходу на кілька потоків.

## Поточний стан

Кадр виконується в одному потоці: ввід, симуляція, оновлення модулів, підготовка і відправлення команд GPU.
Паралельно з ним працює лише GPU (два кадри в польоті).

Причина: важкої роботи, яку варто розпаралелювати, ще немає. Без реальних навантажень неможливо
обґрунтовано спроєктувати розподіл роботи, а помилки синхронізації дорого шукати.

## Правила, що діють уже зараз

Їх мета — щоб перехід на кілька потоків не вимагав переписувати модулі.

| Правило | Чому |
|---------|------|
| Жодного прихованого глобального стану; глобальні змінні лише з префіксом `g_` і обґрунтуванням | спільний змінюваний стан — головне джерело гонок |
| Система отримує дані явно: `std::span` на колонки, які читає, і окремо на ті, які пише | видно, які системи можна виконувати одночасно |
| Читання і запис розділені: система не змінює дані, які в тому самому проході читає інша система | основа для паралельного запуску систем |
| Дані кадру — у `FrameArena`, а не в статичних буферах | кожен потік зможе мати власну арену |
| Лічильники обліку пам'яті й реєстри — атомарні або під м'ютексом | вже зараз безпечні з будь-якого потоку |
| Callback-и бібліотек (GLFW, Vulkan debug messenger) лише записують дані, обробка — в циклі кадру | callback може прийти з іншого потоку |
| Платформа: вікно і події лише з головного потоку | вимога GLFW і більшості ОС |

## Цільова модель: система задач

| Частина | Опис |
|---------|------|
| Пул потоків | робочі потоки за кількістю ядер мінус головний; створюються один раз при запуску |
| Задача | функція з даними; задачі можуть залежати одна від одної |
| `parallel_for` | ділить діапазон (наприклад, колонку `SoaPool`) на шматки і виконує їх на різних ядрах |
| Очікування | головний потік чекає завершення групи задач і сам виконує задачі, поки чекає |
| Пам'ять | `FrameArena` на кожен потік; пули з синхронізацією або на потік |
| Лог | черга повідомлень і окремий потік запису у файл (ADR 0011) |

```cpp
jobs.parallel_for(transforms.size(), 1024, [&](Range range) {
    update_world_matrices(local.subspan(range), world.subspan(range));
});
jobs.wait_all();
```

SoA-дані (ADR 0008) розрізаються на незалежні шматки без копіювання, тож добре лягають на цю модель.

## Порядок переходу

| Крок | Коли | Що |
|------|------|----|
| 1 | перше фонове завантаження ассетів | пул потоків і задачі без залежностей: читання файлів і розбір glTF поза кадром |
| 2 | перша важка масова робота (анімація багатьох персонажів, відсікання) | `parallel_for` над SoA-колонками, `FrameArena` на потік |
| 3 | залежності між системами | граф задач кадру: системи з неперетинними даними виконуються паралельно |
| 4 | якщо профайлер покаже, що підготовка кадру впирається в CPU | паралельний запис command buffers; окремий потік рендеру лише після вимірювань |

Кожен крок — окреме рішення з ADR, після вимірювань (скіл `performance-optimization`).

## Перевірка

- ThreadSanitizer: окремий пресет, коли з'явиться перший робочий потік (несумісний з AddressSanitizer).
- Задачі мають давати той самий результат, що й однопотокове виконання: тести порівнюють обидва режими.
